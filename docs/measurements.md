# 量測紀錄

所有數字都是 `eval/feed.py` 按真實時間（`ffmpeg -re`）灌音訊、走 `docs/protocol.md`
的完整路徑量到的。離線批次跑模型的數字不列在這裡，因為那量不到「推論會不會拖累收音」。

機器：Apple Silicon（arm64）、macOS 26.2、Python 3.11、mlx-qwen3-asr 0.3.5、
模型 `Qwen/Qwen3-ASR-0.6B`。

素材：GitLab Unfiltered《Security Risk Management: Security Policies - Weekly Meeting
- 2026-06-24》（`I5Of6ps2Ec4`，25 分 10 秒，646 個字幕 cue、85 次講者換人）。
Ground truth 是 YouTube **自動**字幕，本身就有錯，所以 WER 只能看趨勢，不能當驗收。

---

## 冷啟動：第一次推論 46 秒

第一次 `feed_audio` 要編譯 Metal kernel，實測 46.3 秒，之後穩態每塊 0.2–0.5 秒。

這件事若發生在會議開始，就是開場前 46 秒全部丟失——正是舊版「不會收音」的體感。
所以 worker 先用靜音預熱，**預熱完才送 `ready`**，client 在那之前不會送音訊。

## chunk_size_sec 掃描（前 120 秒，2026-08-08）

| chunk | partial P95 | final P95 | WER | 判定 |
|---|---|---|---|---|
| 2.0 s | 2407 ms | 2259 ms | 26.3% | partial 不過 |
| **1.0 s** | **362 ms** | **363 ms** | 32.5% | **兩個都過** ← 目前預設 |
| 0.5 s | 5130 ms | 4595 ms | 59.7% | 兩個都不過，且崩潰 |

三件事：

1. **延遲 = 單塊推論時間**，不是佇列堆積。事件抵達時間減音訊位置（lag）幾乎等於
   `infer_ms`，代表音訊進來從來沒有等過推論——獨立 process 這個設計有效。
2. **2.0 秒不是越大越好。** 一塊要吐的字越多，autoregressive 解碼越久，P95 就被
   那些話很密的塊拉到 2.4 秒。
3. **0.5 秒會崩。** 每秒兩次推論的固定成本讓 RTF 越過 1，佇列開始堆積，延遲滾到
   5 秒、WER 掉到 60%。**這就是舊版的死亡螺旋，現在有數字了。**

WER 在 26–32% 之間，離 12% 的 gate 很遠。錯誤分布裡**插入**最多（28 / 40 / 79），
來源是 streaming 的重複輸出（同一句話講兩次），不是聽錯。

## endpointing：energy 比 fixed 差（否定結果）

假設是：`fixed` 每秒硬切會切在字中間，造成逐字稿破碎和邊界重複；改成 `energy`
（切在能量低點，也就是講話停頓）應該會好。**實測相反**，同樣前 120 秒、chunk 1.0：

| endpointing | partial P95 | final P95 | WER |
|---|---|---|---|
| **fixed** | **360 ms** | **367 ms** | **32.5%** ← 預設 |
| energy | 4293 ms | 4686 ms | 34.2% |

energy 模式會等到偵測到停頓才切，開會的人講話少有乾淨停頓，於是一塊拖到很長，
單次推論時間跟著爆掉，延遲 P95 4.3 秒。WER 也沒有變好。維持 `fixed`。

## 全長跑：25 分鐘，延遲不漂移

| | 前 120 秒 | 全長 1509.7 秒 |
|---|---|---|
| partial P95 | 362 ms | **381 ms** |
| final P95 | 363 ms | **382 ms** |
| WER | 32.5% | **29.4%** |

事件 1441 個 final、1509 個 partial，沒有 `gap`、沒有 `error`、沒有丟幀。

**這是最重要的一個數字**：25 分鐘後的 P95 跟 2 分鐘時一樣。舊版的死法是「越講越
落後」——延遲會隨時間單向增長。這裡沒有，代表推論確實沒有卡在收音路徑上。

## 分析層開著，延遲沒有變（2026-08-08，前 180 秒）

`claude` CLI 是很重的 node process，跟 ASR 搶的是同一顆 CPU，所以「開分析會不會
拖垮收音」必須量。前 180 秒、`discussion` 場合、網路查證開：

| | 只有 ASR（前 120 秒） | 分析開著（前 180 秒） |
|---|---|---|
| partial P95 | 362 ms | **387 ms** |
| final P95 | 363 ms | **378 ms** |

事件 165 個 final、4 個 insight，沒有 `gap`、沒有 `error`、沒有丟幀。

前提是 `nice -n 15`。**不加的時候實測會炸**：單次推論從 0.37 秒被拖到 54 秒，
音訊佇列塞爆開始丟包——跟 0.5 秒 chunk 那個死亡螺旋是同一種。分析可以慢，收音不能停。

副作用一則：會議結束時還在跑的那一輪分析，回來會往關掉的 socket 送，變成沒人接的
task exception，而且 CLI process 留在背景繼續吃 CPU。收工要主動取消並 `kill`。

## 中文：37.6%，跟英文同一個量級（2026-08-08，前 120 秒）

產品要錄的是中文與中英夾雜的會議，英文數字不算數，所以另外抓語料：`6h6VsrclFTI`
（塞掐 Side Chat E417，66 分鐘，前 Meta 資料科學家訪談），**手動 zh-TW 字幕**——
真人打的逐字稿，比英文那份自動字幕可信。

| 設定 | partial P95 | final P95 | WER | 判定 |
|---|---|---|---|---|
| **0.6B、語言自動** | **478 ms** | **479 ms** | **37.6%** | ← 預設 |
| 0.6B、鎖 `zh` | 588 ms | 588 ms | 37.8% | 沒有比較好 |
| 1.7B、語言自動 | 3196 ms | 3239 ms | 35.1% | **兩個延遲都爆** |

三個結論：

1. **鎖語言沒有用。** 37.8% vs 37.6% 在同一個雜訊區間。中英夾雜用自動判斷比較安全。
2. **1.7B 不值得。** WER 只從 37.6% 進步到 35.1%（2.5 個百分點），延遲卻是 8 倍。
   單塊推論中位數 982 ms、最大 1457 ms，對上 1.0 秒的 chunk 就是 RTF ≈ 1，
   佇列開始堆積——跟 0.5 秒 chunk 那次是同一種死亡螺旋，只是從另一邊踩進去。
   README 排第一的槓桿（換大模型）到此為止：這個家族只有 0.6B 和 1.7B 兩個權重。
3. **模型吐簡體。** 使用者是台灣人，讀起來就是不對；拿繁體逐字稿當 reference 時，
   每個簡體字還會算一次取代。在 worker 的事件出口統一轉繁：**WER 55.2% → 37.6%**，
   取代從 185 掉到 83。這不是調參數，是原本就少做的一步。

### 兩個把數字弄假的陷阱

**手動字幕不一定是逐字稿。** 第一次抓的中文語料 `qWbAyRrT-Ew` 有手動 zh-TW 字幕，
但受訪者講英文——那是**翻譯**字幕。ASR 正確吐出英文，reference 是中文，WER 算出
80.7%，全是假的。`eval.corpus` 現在會比對影片的 `language` 欄位並警告。

**`unfixed_token_num` 動不了 WER。** README 排第二的槓桿，實測把它從 5 開到 15、
`unfixed_chunk_num` 從 2 開到 3，輸出**一個字都沒變**（37.61%、插入 101，
與預設完全相同）。看套件原始碼就知道為什麼：它只決定 `stable_text` 切在哪，
而逐字稿來自 `state.text`（合併後的權威全文）。邊界重複產生在合併那一層，
不在穩定判定那一層。這條槓桿劃掉。

剩下的插入錯誤（101 個，佔錯誤大宗）長這樣：

    ref:  在三月中的時候就有聽到謠言了 人心惶惶
    hyp:  在三月。月中的。時候就有聽。聽到謠言。呃，人心。心慌慌了，

每塊的開頭重講一次上一塊的結尾。要修得動這個，得處理合併層，不是調參數。

### 合併層：標點不敏感的重疊比對，37.6% → 35.6%

套件的 `_append_chunk_text` 用**完全相符**的 unit 前後綴找重疊。模型重講同一段時
標點常常不一樣（`在三月。` 接 `月中的。`），比對就失敗，兩塊直接接起來。改成忽略
標點再找一次重疊，並且把 curr 尾端那個硬斷出來的句號拿掉：

| | 預設合併 | 標點不敏感 |
|---|---|---|
| WER | 37.6% | **35.6%** |
| 插入 | 101 | **90** |
| final P95 | 479 ms | 523 ms |

    before: 在三月。月中的。時候就有聽。聽到謠言。
    after:  在三月中的。時候就有聽到謠言。

跟換 1.7B 一樣是 2 個百分點，但**不用付延遲**（1.7B 要付 8 倍）。

代價要講清楚：這是 monkey-patch 套件內部函式，升級 `mlx-qwen3-asr` 要重驗。
另外真實的口語重複會被吃掉一次（`對對` + `對啊` → `對對啊`），重疊上限 12 個 unit
就是為了不讓它吃更多。

## 講者分離：GPU 是共用的，工作週期才是旋鈕（2026-08-08，前 120 秒）

pyannote `speaker-diarization-community-1` 不是串流模型，只能對一整段音訊分群。
選「對目前為止的整段重跑」，因為只看最近視窗的話，每個視窗各自分群，`SPEAKER_00`
在前後視窗不是同一個人，標了等於沒標。

| 裝置 | 120 秒音訊 | RTF |
|---|---|---|
| **MPS** | **10.3 s** | **0.086** |
| CPU | 80.0 s | 0.667 |

CPU 慢 7.8 倍，30 分鐘的會議一輪要 20 分鐘，不可行。所以 diarization 跟 ASR 搶同一顆
GPU，而**這件事有代價，量得出來**：

| 讓出 GPU 的倍數 | partial P95 | final P95 | 120 秒內跑幾輪 |
|---|---|---|---|
| 關閉 diarization | 478 ms | 479 ms | — |
| 倍數 3（吃 25% wall time） | **1832 ms FAIL** | 700 ms | 4 |
| **倍數 8（吃 11%）** | **702 ms PASS** | 714 ms | 3 |

「跑完休息這次耗時的 N 倍」就是那個旋鈕，預設 8 是這張表選出來的，不是猜的。
倍數 3 直接讓 partial 破 800 ms 的 gate——**逐字稿不能停，講者標籤可以晚到**。

兩件實作上非知道不可的事：

1. **pyannote 每次重跑會把 cluster 重新編號**：同一個人上一輪是 `SPEAKER_02`、下一輪
   變 `SPEAKER_01`。UI 若直接顯示這個 id，講者名稱會在會議中亂跳。改成照「第一次
   出現的時間順序」命名（講者 1、講者 2…），那個順序對重新編號免疫。
2. **講者標籤是回填的**。舊 PRD 那條「講者切換辨識延遲 < 2 秒」在這個架構下做不到，
   也不值得為它換掉逐字稿的即時性。

## WER 還差得遠

29.4%，gate 是 12%（而且 gate 講的是繁中人工逐字稿，這裡是英文自動字幕，標準更寬）。
逐字稿看得懂但品質差，典型錯誤：

    ref:  Hey everyone, welcome to this week's security policies weekly meeting.
    hyp:  The. Hey everyone. Welcome this week. Security. Security policies weekly meet.

三種錯：邊界重複（`Security. Security`）、破碎成短句、無中生有的填充詞（`The.` `I.` `A.`）。

還沒試的槓桿，依預估效益排序：

1. **換大一點的模型**——現在是 `Qwen3-ASR-0.6B`，是這個家族最小的
2. `unfixed_token_num` / `unfixed_chunk_num`——控制尾巴保留多少可改寫空間，直接對應邊界重複
3. `context` 餵會議專有名詞（人名、`fastboot` 這種被聽成 `fast food` 的字）
4. `finalization_mode` / `enable_tail_refine`
